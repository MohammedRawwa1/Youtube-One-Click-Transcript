# Changelog

All notable changes to **YouTube One-Click Transcript** are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

This changelog starts at 1.2.0 (earlier releases were not tracked).

## [Unreleased]

### Added
- **The chunk session says how much of the transcript has been copied.** Stepping through the parts of an oversized copy now shows the share of the whole transcript already on the clipboard: the main button carries it in its label (`⏭ Copy 2/5 · 43%`), the compact chapter and player badges carry it in their own (`⏭2/5 · 43%`) as well as in their tooltip, and the debug report gained `progress=<n>%`. The share is counted from the text actually copied — each part contributes its segments plus the joining space, the same way the parts were sized — so it grows with what was copied rather than with the part index, and it reaches exactly 100% on the last part. It is read after the part has been written, so nothing in flight is counted. The percentage follows the page's numerals and takes the locale's own percent sign (`٪`, and the spacing German puts before it), exactly like the `n/N` counters beside it.
- **The chapter row reserves the room a wide pill takes.** A compact badge is absolutely positioned, so a pill does not push the chapter title aside — it lands on top of it, and the end of a long title is exactly where it lands. Measured in Chrome, the share takes the badge from a 34px pill to a 63px one (91px at the extreme of a three-digit count), so the row is now told the width the badge actually rendered at — measured after the label is set, so it is right for any wording, digit set and part count — and reserves exactly that through `content.css`, applied to the rows whose badge sits beside the title (the classic description rows and the horizontal chapter-list items). A vertical chapter card is deliberately left alone (its badge sits over the thumbnail, so reserving inline room there would only squeeze the card), as is the player's badge, which shares a flex row that reflows on its own.The room is given back to the title as soon as the badge goes idle.

### Changed
- **The main Transcript button batches by size, never by chapter.** The two copy operations were sharing one chunking algorithm, one pair of size constants, and — for a long video with chapters — one set of boundaries: a full copy over the threshold was cut into one piece per chapter, each labelled with its chapter title. A 19-hour chaptered recording therefore did not batch like the 4–8 hour ones (which stayed under the threshold and copied in one write); it fell into the chapter path instead. The main button is now its own batcher over the whole transcript: it hands the part builder a single untitled span (the video), so its parts are `Part i/N` at segment boundaries, and it never reads the chapter list — a chaptered recording batches exactly like a chapterless one.
- **Each operation now has its own size pair.** `CHUNK_THRESHOLD` / `CHUNK_MAX_CHARS` are replaced by `MAIN_CHUNK_THRESHOLD` / `MAIN_CHUNK_MAX_CHARS` for the main button and `CHAPTER_CHUNK_THRESHOLD` / `CHAPTER_CHUNK_MAX_CHARS` for the chapter and player badges, all of them 1M, and `buildChunks(span, rows, maxChars)` receives the ceiling as an argument instead of closing over a shared constant. Retuning one operation can no longer move the other, and the builder no longer takes a chapter list at all — a chapter badge hands it that one chapter, the main button hands it the whole video.
- **The part size is derived from the data, not from a fixed target.** The 1M-character ceiling is the only number the extension still imposes; how a copy is divided is computed from the rows the caption source actually returned — as few parts as the ceiling allows, sized evenly, with the target for each part being the text still unplaced shared over the parts still to come. A 2.1M-character transcript is now three ~700k parts instead of 1M + 1M + a 100k tail, and there is no size that falls through the cracks between a threshold and a cap. The size test the callers use to decide whether to batch (`rowsLength()`) is the same measurement the splitter uses, so the decision and the split can never disagree by a character.
- **The parts are verified lossless before the first write.** Every segment lands in exactly one part, in order, so the parts reassemble into the collected transcript byte for byte; a partition that would drop, duplicate or truncate text — or that would send a part over the ceiling while holding more than one segment — throws instead of being pasted. A single segment longer than the ceiling still gets its own part whole: cutting a caption in half to satisfy a size limit would lose text, which is the one thing this must never do.

### Tools
- **`tools/check-badge-layout.mjs`** (`npm run check:layout`) — the check that needs a real browser, because it is about rendered text width. It launches Chrome headless with a throwaway profile, inlines the real `content.css`, injects the real `setChunkLabel()` / `reserveBadgeRoom()` / `resetMainButton()` and lays the badge out against a deliberately long chapter title in every place the extension injects one — classic description row, horizontal chapter-list item, vertical chapter card, the player bar, and a mirrored RTL row — asserting that a pill never covers the title, never escapes its row, and never squeezes a card that does not need reserving. It also asserts the check can fail: with the reservation disabled the wide labels must overlap. The fixture rows are a model of YouTube's DOM, which is the one thing it cannot prove; the pill widths it measures are real.

### Tests
- `test/test_chunks.mjs` now pins the share as well, with deliberately uneven part bodies so a share taken from the part index (33/67/100) would fail: it is 11% after the first part and 41% after the second, on both badges' labels, in the tooltip and in the report. It also pins the room reservation — that the measured width (plus the gap) is what the row is told, that the main button and a non-chapter parent are left alone, that an unmeasurable badge reserves nothing rather than guessing, that the room is given back on idle, and that the class/content.css contract really lines up (both row selectors, the vertical card excluded). It also pins each operation separately: a span under its ceiling is one piece, rows outside the span are ignored, the ceiling is per call (so the same rows can be one part for one node and several for the other), both constant pairs start splitting at or below their own ceiling, the parts come out even rather than full-then-stub, `rowsLength()` agrees with the splitter, and — because a regression here would look plausible in the output — that the main copy handler references `wholeVideoSpan()` and `MAIN_CHUNK_MAX_CHARS` and never `getChapters`. The partition itself is checked across a spread of sizes and ceilings, and the losslessness guard is exercised directly with dropped, duplicated, reordered and overfull partitions.

## [1.7.0] - 2026-09-22

### Added
- **Caption language selection (`ytxt_lang`).** `localStorage.setItem("ytxt_lang", "ar")` (or `#ytxt_lang=ar` on the video URL) asks for a specific caption language. A track in that language is used when the video has one; otherwise the default track serves it through YouTube's own `tlang` translation. Without a preference, the copy uses the video's **own** caption language — the one the page itself would show, taken from the default audio track's caption index and falling back to the first listed track. This matters because the previous rule picked the *first non-ASR* track, which is a language decision made by accident: an Arabic video offering Arabic auto-captions plus a manual English track would copy the English translation.
- **`capLang` / `capLangMismatch` diagnostics**: the debug report, the overlay and `data-debug` now say which language the rows that answered are in, and flag when an explicitly requested `ytxt_lang` could not be honored by the source that answered (`capLang=ar capLangMismatch=yes`).
- **`test/test_arabic.mjs`** — a dedicated suite for Arabic/RTL behaviour: localized timecodes, Arabic chapter titles, language-aware track choice, `tlang`, `get_panel` parsing and RTL part markers.

### Added
- **Optional UI label table (`ytxt_ui`).** The extension's own labels — the transcript button and its chunk states, the chapter/player badge tooltips, the chunk instruction, the debug overlay and every alert — can now be written in another language. `ytxt_ui` = a language code, or `auto` to follow the page; English stays the default and remains the fallback **per key**, so a partial table cannot leave a label missing. Arabic is built in, and `ytxt_ui_strings` lets a user add a language or override single labels without editing the extension. Placeholders (`{title}`, `{count}`) are filled at the call site, where a chapter title keeps its bidi isolation inside the translated sentence. The debug report's field names and values are deliberately excluded — only the human `label.*` entry is translated — so reports stay comparable between users. Separate from `ytxt_lang`, which chooses the *caption* language.
- **Chunk counters follow the page's numerals.** `⏳1/3` / `⏭2/3` (and the numbers in the chunk instruction and the tooltips) are now formatted in the digit set the page's language uses — Arabic-Indic on an Arabic UI, Persian-Indic on a Persian one, ASCII elsewhere — so the labels no longer look foreign next to YouTube's own. Intl picks the digit set; the two cases it gets wrong for this purpose are handled explicitly: a region-less `<html lang>="ar"` resolves to *Latin* digits in ICU, so the region-less tags whose regions commonly use non-Latin digits are pinned, while a regioned tag (`ar-MA`, `ar-EG`) is always left to Intl. `ytxt_numerals` = `latn` / `arab` / `arabext` overrides it. Deliberately not applied to the copied transcript's `(part i/N)` markers, which are content and stay greppable, or to the debug report's field values, which have to stay comparable between users.

### Fixed
- **Localized timecodes dropped content.** `parseTimecode` matched only ASCII digits, so on a page whose numerals are Arabic-Indic (`٥:٠٨`) or Persian-Indic (`۵:۰۸`) every string timestamp failed to parse: `get_panel` responses looked segment-less, the panel scrape collected *nothing* (rows are keyed by timestamp), the chapter shelf resolved to no chapters — so per-chapter buttons and chapter-boundary chunking disappeared — and the video duration was unknown. Both digit ranges (and bidi marks around a value) are now folded to ASCII first, losslessly: the ASCII path is untouched, and the fixture-based suite pins that.
- **Arabic-only chapter titles were deleted** by the description fallback: `/^[^a-zA-Z0-9]+/` strips leading non-alphanumerics, and *every* character of an Arabic title is non-alphanumeric by that class, so the title became empty and the chapter was discarded. Titles are now stripped of leading punctuation/marks only (`\p{L}\p{N}` under the `u` flag), and the timecode pattern is matched on a digit-folded copy of the line so Arabic-Indic timestamps resolve chapters too. Digits an author wrote inside a title are left exactly as written.
- **RTL chunk headers were reorderable.** `Chapter Title (part 1/3)` with a right-to-left title lets the bidi algorithm move the marker against the title and pair its parentheses with neighbouring text. The marker alone is now wrapped in an LRI/PDI isolate for RTL titles; a Latin title is byte-identical to before.
- **Mirrored (RTL) layout, and the last two bidi gaps.** The per-chapter badge was positioned with a physical `right: 6px`, so on a watch page mirrored for Arabic or Hebrew it could sit on top of the chapter title it belongs to — the badge and the debug overlay now use logical insets (`inset-inline-end`) and the main button `margin-inline-end`, all of which follow the row's own direction. The overlay's summary line now isolates an RTL `Chapter: <title>` label for display only, so the diagnostics around it keep their order while the JSON report that the Copy button puts on the clipboard stays byte-identical. And a title that is nothing but a number written in Arabic-Indic digits is now rejected as a bare-number fragment, exactly like `27` already was.
- **RTL tooltips and overlay text.** The same reordering affected every label that embeds a chapter title in a fixed English sentence — the per-chapter badge ("Copy transcript of chapter: …"), the player badge, and the chunk session's "paste chunk n, then click again" instruction — where an Arabic or Hebrew title could drag the sentence's punctuation and separator around it. Those values are now wrapped in an FSI/PDI isolate (a Latin value is byte-identical). The debug overlay is guarded the same way but in CSS only (`unicode-bidi: plaintext`), deliberately **not** by inserting control characters: its Copy report button puts that text on the clipboard, and the report has to stay byte-identical for tooling.

## [1.6.2] - 2026-09-14

### Fixed
- **The previous video's transcript was copied after an in-page navigation** (playlist next/previous, a related-video click, a chapter link) — it only became correct after manually refreshing the browser. YouTube is a single-page app: the inline `ytInitialPlayerResponse` / `ytInitialData` scripts are written once on the first hard load and are **not** rewritten when the page moves to another video, so the caption track resolved from that payload was the previous video's. Captions and chapters are now resolved per video, and a payload that names a different video than the URL is discarded:
  - the video id used for the `get_panel` / `get_transcript` requests now always comes from the URL, which is the only description of "the video playing right now" that is current in every context;
  - the player's own response (`movie_player.getPlayerResponse()`, `ytd-watch-flexy.playerData`) is preferred wherever the JS world exposes it, because YouTube does update it on every navigation;
  - chapter data is read from the live sources first (player response, rendered chapter shelf), so a playlist jump cannot attach the previous video's chapters either;
  - the discarded payload's video id is reported as `staleBlob` in the debug line, the overlay and `data-debug`, so a mis-detection is visible instead of silent.

- **The cap was ignored on videos without chapters.** Chunking required two or more chapters, so a video with none (or exactly one) wrote its entire transcript in one clipboard call however large — a 5M-character transcript was a single write. The cap limits one clipboard write, so it now applies whenever the text exceeds it, and the chapter list only decides *where* the splits fall: on chapter boundaries when there are two or more, on segment boundaries across the whole video otherwise. Parts of a chapterless video are numbered `Part 1/10` rather than being called chapters, and an unsplit one still gets no header line at all (byte-identical to before).
- **A rejected single write had no recovery.** A piece that fit the cap was written in one go, and if the clipboard refused it the user got an error and nothing else — which is exactly the size-sensitive case, since the `execCommand` fallback used when `writeText` is unavailable lays the text out in a hidden textarea first (reported to struggle from roughly 180k characters). A rejected write is now retried as an ordered part sequence, so the copy degrades into `n/N` parts instead of failing. If there is nothing to split, or the parts fail as well, the original error is reported rather than swallowed.
- **A failed chapter part left a live chunk session behind.** When the first part of an oversized chapter could not be written, the badge went back to its idle glyph but the session stayed live — so the next click silently resumed the sequence the user had just watched fail, instead of starting a fresh copy. The main button already cleared its session on failure; the chapter path now does the same, so a failure behaves identically wherever it happens.
- **The panel-scrape fallback could read the previous video's rows.** YouTube's transcript panel is an engagement panel that outlives an in-page navigation and is repopulated asynchronously, so for a moment after a playlist jump its DOM could still hold the video you just left. The rows that were on screen when the navigation began are now remembered, and a panel still showing them is closed and re-opened (back through the native button) and required to actually change before its content is used — if it cannot be refreshed, the copy fails with a clear message instead of pasting the wrong video's text. This path only runs when all three caption sources fail, so the fix costs nothing on a normal copy.

### Changed
- **The per-chapter buttons chunk too.** A chapter used to be one clipboard write however long it was, so a single 3-hour chapter inside a stream became one enormous paste with nothing to say how much was left — and unlike the main button, it had no `n/N` counter at all. A chapter longer than the cap is now copied as ordered parts, split on segment boundaries so no part cuts a caption in half, with the button showing the count (`⏭2/3`; the compact 22px buttons omit the words, the main button still says `⏭ Copy 2/3`). A chunk session is owned by the button that started it, so pressing **Transcript** mid-sequence starts a fresh full copy rather than resuming a chapter's parts. The compact badges are circles sized for a single glyph, which cannot hold `⏭2/3`, so a badge showing a count widens into a pill and returns to a circle as soon as the count is gone — and the chapter tooltip it overwrote ("Copy transcript of chapter: …") is restored with it.
- **The chunking threshold is 1M characters instead of 500k.** This is the size above which the main Transcript button copies in chunks rather than in one write. A 19-hour lecture or stream is commonly only a little over 1M characters, so at 500k a chaptered course was cut into one piece per chapter (100+ clicks) when the whole transcript would have pasted from a single click. At 1M characters — ~2 MB as UTF-16 — ordinary long videos copy whole again, and only genuinely enormous transcripts are chunked; the per-chapter and per-part behaviour described below is unchanged.
- **Chunk mode copies bigger pieces: `CHUNK_MAX_CHARS` is 1M instead of 100k** — the largest amount this extension will put in one clipboard call, deliberately equal to `CHUNK_THRESHOLD` so a single chunk can never be larger than the size already treated as pasteable in one go (a unit test now keeps the two in step). Chunks are one per chapter by default, so the cap only decides when a single long chapter has to be split; at 100k it was the cap, not the chapters, that forced most of the splitting, which is why a long chaptered video took 10+ clicks. Sizing it turned out not to be a clipboard question: Chromium's 256 MiB clipboard cap (`kMaxClipboardSize`, crbug.com/1164680) is applied to **reads**, `WriteText()` sets the data with no size check, `navigator.clipboard.writeText` documents no size limit (its only named failure is `NotAllowedError` — permission, secure context and focus), and Windows has no pre-set clipboard maximum at all. 1M characters is ~2 MB as UTF-16, ~0.4% of that cap; the only size-sensitive route is the `execCommand` fallback used when the async clipboard API is unavailable, which has been reported to struggle from roughly 180k characters — and a write it rejects is recoverable, because the same text is re-split into ordered parts rather than failing. Extensions run on phones as well (Firefox for Android, Kiwi and friends), where the async clipboard path is the same API and a couple of megabytes is not a problem to hold or write. The button's `n/N` counter and the `Chapter Title (part i/N)` titles are unchanged; there are simply fewer parts.
- **A copy in progress is abandoned when the page navigates.** A slow fetch for the video you just left can no longer paste its transcript over the new one, and can no longer leave the button stuck on a spinner. Invalidation happens on `yt-navigate-start` rather than when the new video is ready, because anything already in flight belongs to the video being left.
- **Chapter copy buttons are rebuilt when the chapter changes** — the title is compared as well as the start time — so a DOM node reused across a navigation cannot copy the wrong range.
- The main button is reset on navigation, so it cannot carry the previous video's label into the new one.

## [1.6.1] - 2026-09-04

### Added
- **Console noise filter.** Silences known-harmless console messages from YouTube's page code and other extensions — YouTube's Polymer `LegacyDataMixin` deprecation notice, its PWA `beforeinstallprompt` banner note, and the repeated `A listener indicated an asynchronous response...` errors that *other* extensions' messaging throws on navigation (e.g. Tampermonkey during playlist jumps — thrown by Chrome when an `onMessage` listener returns `true` but its channel closes; this extension has no `chrome.runtime` messaging, so it can never be the source). Only exact known patterns are filtered; everything else — including this extension's own failure reports — passes through untouched. Takes effect when the script runs in the page's own JS world (Tampermonkey `@grant none`); as an MV3 content script it's a no-op because the page's console is out of reach. Opt out with `localStorage.setItem("ytxt_noise_filter", "0")`.
- **Documented the unfilterable noise in the README.** Browser-level warnings (`migrate_from`, `preloaded using link preload`, `powerPreference ... ignored`) and network failures (401 / CORS / `ERR_FAILED`) are printed by Chrome itself, not through the page's console API, so no page or extension code can intercept them — they can only be hidden with the DevTools console filter (exact filter in the README).

## [1.6.0] - 2026-09-04

### Changed
- **Full transcripts copy in one click again.** The chapter-by-chapter mode for the main Transcript button now only kicks in above ~1M characters (roughly 20+ hours of speech) instead of ~100k — a typical 2-6h course or podcast transcript (100k-400k chars) is copied whole in a single clipboard write. The full text was already collected in memory before the threshold was applied, so this only changes *when* the copy is split, never what is copied.
- **Caption sources are now the primary path, not the last resort.** Both the full-transcript copy and every per-chapter copy now fetch the exact caption data first (timedtext → `get_panel` → `get_transcript`), which returns the entire transcript in one request (`get_panel` even for PO-token-gated videos), and only fall back to opening/scrolling YouTube's transcript panel when every caption source fails. Chapter copies no longer depend on the slow, fragile panel scrape succeeding first — and when the panel UI changes again (e.g. a chapter-panel layout with no rendered segments), copies keep working off the caption data.
- **`fetchCaptionsFallback` gained a `primary` flag**: caption-fetch invocations that are the main attempt no longer inflate the `fallbacks` diagnostic stat — only rescues of a failed panel route count as fallbacks now.
- **Chunk mode caps every chunk at ~100k characters.** When chunk mode is active, a single oversized chapter (e.g. one 3-hour chapter inside a stream) is split into `Chapter Title (part 1/N)` pieces at segment boundaries, so no clipboard write in chunk mode is ever huge. The chunk list is now built by a dedicated `buildChunks` helper (covered by a new unit suite, `test/test_chunks.mjs`).

### Fixed
- **`durationMs` in the debug report was always 0** — the code that measured it was lost in an earlier refactor. It now measures the real elapsed time of each copy operation, so reports show actual timings again.
- **Panel fallback raced ahead of YouTube's own rendering.** When the panel shell opened but its segments render asynchronously (and after the caption chain had already failed), `loadTranscriptSegments` could find no scroller and return an empty collection in a few ms, failing the copy with "No transcript text was loaded" even on videos that have one. It now waits up to ~12s for the first segment before giving up (covered by a new collector test — late-rendering panel is waited for and fully collected).
- **The full-copy path never retried the caption chain before failing** (the per-chapter path did). Both paths now give the caption chain one retry on the failure leg, so a transient server rejection gets a second chance.
- **Errors now say why.** The alert after a failed copy used to show only the panel error (e.g. "Transcript button not found") while the real per-source rejections sat hidden in the debug report. Alerts now append `Caption sources all failed: <timedtext/getpanel/innertube reasons>` so a failure is self-explanatory without opening the console.

## [1.5.0] - 2026-09-04

### Added
- **`get_panel` caption source** (the modern transcript panel API) as a new fallback, tried after timedtext and before `get_transcript`. It sends the same gzip-compressed request the YouTube page itself makes (`panelId: "PAmodern_transcript_view"` + a deterministic protobuf `params` carrying the video id + the page's visitor data) and parses `transcriptSegmentViewModel` rows. Live-verified: it returns the **entire transcript of a 7-hour video in a single response, without a PO token** — rescuing videos whose timedtext URLs are PO-token-gated. Degrades gracefully: if the video id, `CompressionStream`, or the page's visitor data is missing, or the request fails, the chain falls through to the next source and the reason is reported in `capFail`.
- **Innertube `get_transcript` fallback** as a third caption source (protobuf params, page-derived API key/client version with pinned fallbacks, `cueGroups` parsing). Live-verified that YouTube currently rejects it with HTTP 400 `Precondition check failed` (the current UI no longer uses the endpoint), so it is a best-effort last resort whose rejection is reported precisely.
- **`capSource` diagnostic stat**: which caption source produced the rows (`timedtext` / `getpanel` / `innertube`), shown in the console report, the debug overlay, and the `data-debug` JSON. Chunk-mode reports now preserve the caption-source provenance instead of wiping it on every chunk click.
- **PO-token detection**: timedtext URLs flagged `exp=xpe` are detected; when such a track fails, the report explains the botguard PO token requirement and the pointless retry is skipped (non-gated URLs keep their existing retry behavior).
- **Precise fallback failure reporting**: `capFail` now combines all three legs (e.g. `timedtext: caption response was empty [PO-token-gated...]; getpanel: getpanel error 400 (...); innertube: innertube error 400 (...)`), surfacing YouTube's own rejection messages.

### Changed
- Caption-source fallback order is now: timedtext → `get_panel` → `get_transcript`.

## [1.4.0] - 2026-09-04

### Added
- **Caption-fetch retry**: the timedtext fallback now retries once (after a short pause) when YouTube returns a transiently empty response (HTTP 200 with no body) or a response with no text events. ASR caption availability for the same video varies between sessions, and this gives gated videos a second chance before the copy fails.
- **`capRetries` diagnostic stat**: the debug report now records how many times the caption fetch retried.
- **Rendered-chapters-shelf fallback**: chapter resolution now has a new source that reads the rendered Chapters shelf cards directly from the DOM (deduped by start time, since YouTube renders the same shelf multiple times). Verified to match the page-data markers exactly, it works even in sessions where YouTube's JSON page variables can't be parsed.

### Fixed
- **Chapter parsing is now consistent across sessions.** The description-text fallback was scanning the whole watch-metadata blob and could fabricate "chapters" from stray timestamps (view counts, durations) — e.g. garbage entries like `86: 27` — so the same video could resolve different chapter lists depending on which sources were readable. The description parser is now scoped to the description itself and rejects all-digit titles.
- **Caption-fetch failures are diagnosed precisely.** The response body is read before judging, so reports now distinguish `caption response was empty` (HTTP 200, no body) from `caption response was not JSON`, HTTP status errors, and missing tracks — instead of lumping them into one generic reason.

### Changed
- Chapter resolution now follows an authoritative chain: `ytInitialData` markers → player-response markers → **rendered Chapters shelf** → scoped description text. Combined with the fixes above, the same 7 chapters resolve in every session and layout, so chunk boundaries in the transcript copy always match the player's chapters.

## [1.3.0]

### Added
- **Opt-in diagnostics**: enable with `localStorage.setItem("ytxt_debug", "1")` or `?ytxt_debug=1` / `#ytxt_debug=1` on the video URL. Every copy operation then prints a one-line report to the console (source, rows collected, sweep steps, incomplete flag, fallbacks used, `capFail` reason, range, duration), mirrors the same stats as JSON on the main button's `data-debug` attribute, and shows an on-page overlay with a one-click **Copy report** button (full JSON including video ID) for bug reports.
- **Transcript-collector completeness safeguards** in `loadTranscriptSegments`:
  - Full copies use the video's known duration as a reach target, so a stall caused by YouTube's list virtualization is detected rather than mistaken for the end of the transcript.
  - A repair sweep walks the list top→bottom one viewport at a time when DOM rows were discarded mid-scroll (virtualized lists) or the fast pass stalled short, forcing YouTube to re-render every window.
  - A gap audit flags the result as `incomplete` when two consecutive collected timestamps are more than 30s apart.
- Both the full/chunked copy and per-chapter copies now honor the `incomplete` flag: they fall back to the exact caption fetch, and fail loudly ("Transcript loaded incompletely") when no caption source exists — a transcript with silent holes is never pasted.

### Fixed
- The full-copy path could continue with gappy panel text when the panel came back incomplete and the caption fallback also failed; both copy paths now behave identically and fail loudly.
- A clipboard write failure mid-chunk-session left the session alive, so the next click silently resumed at the middle chapter; the session is now aborted on any failure so the next click starts fresh.
- Rapid SPA navigations could leave two player-button tick loops running; the restart timeout is now tracked and cleared.
- Removed the dead `.my-yt-chapter-busy` class toggle (set on every button state change but never styled or read).

## [1.2.0]

### Added
- **Current-chapter copy button in the player scrubber**: a small copy button appears next to the visible chapter title in the player's control bar. It resolves the playing chapter from the real playback time on every tick, retargets as playback crosses chapter boundaries, and copies that chapter's slice of the transcript.
- **Chapter-by-chapter chunked copy for the main Transcript button**: when a video's full transcript exceeds ~100k characters and the video has chapters, the first click copies chapter 1 (prefixed with its title), the button becomes a "copy next chunk" control, and each click copies the following chapter until all are copied — so very long transcripts can be pasted in manageable, self-describing pieces.

### Baseline at this version
- 📜 **Transcript** button next to Like/Share: opens YouTube's transcript panel, scrolls through it to collect every segment (handles long videos where YouTube only renders part of the transcript at a time), and copies the text in one click.
- 📋 **Per-chapter copy buttons** on every chapter in the video description (both the newer chapter cards and the classic list rows): click one to copy just that chapter's range of the transcript, prefixed with the chapter title.
